# Flutter 空壳应用模板开发 Phase Plan

> 日期：2026-11-01
>
> 状态：待实施计划。阶段完成条件均需通过实际代码、测试和平台验证确认，本文不代表相关能力已经交付。
>
> 设计依据：[Flutter 空壳模板开发说明](flutter-template-development-revised.md)。本计划与开发说明共同维护；若实施中调整设计，须同步更新相关契约、验收标准和计划。

## 1. 目标与范围

开发可运行、可复用的 Flutter 空壳应用模板，作为团队创建各类 Flutter App 的统一起点，减少重复搭建，并统一基础能力和工程约定。

首版以 Android 为必验平台，iOS 为兼容目标且不设验证阶段门。模板默认无需业务后端或第三方账号即可启动，提供首页、设置页及最小使用示例。派生应用独立扩展品牌、业务页面、后端协议和平台模块。

本文不关联文档存放目录中的现有项目。模板工程位置、工程名称、包名和原生应用标识在 Phase 0 确定；本计划不授权创建或修改其他工程。

## 2. 推进方式

按 7 个阶段、3 个里程碑推进。先验证工程能够稳定运行，再完善通用能力，最后验证模板能否实际用于创建新 App。

阶段依赖顺序为 Phase 0 → Phase 1 → Phase 2 → Phase 3 → Phase 4 → Phase 5 → Phase 6。测试和 CI 随功能持续补充，Phase 5 负责整体质量及平台验收。

每个阶段交付代码、可重复命令、验证记录和未解决项。阶段完成后才能标记相应能力已交付；后续阶段不能替代前序阶段的验证。

## 3. 阶段计划

| 阶段 | 目标 | 主要工作 | 交付物 | 阶段完成条件 |
| --- | --- | --- | --- | --- |
| **Phase 0：实施基线** | 明确工程与工具链 | 确定工程名称、标识及存放位置；固定 Flutter/Dart；确定核心依赖候选版本、原生工具链和最低系统版本；明确 Android 验证环境 | 工程决策记录、工具链配置、首版任务清单 | 每项关键选择均已记录；Android 验证环境有明确执行方式；候选组合在 Phase 1 构建通过后转为正式基线 |
| **Phase 1：最小工程骨架** | 获得可重复构建的起点 | 创建独立工程；建立目录、lint 和测试入口；配置开发/测试/生产逻辑环境；建立基础 CI | 可运行工程、锁文件、最短启动说明、基础流水线 | 干净检出后依赖解析、静态分析、测试、Android debug 构建通过 |
| **Phase 2：启动与核心界面** | 建立稳定的应用外壳 | 实现启动协调器、失败页及重试；接入 Riverpod 和稳定路由器；实现首页、设置页、未知路由页；完成主题与国际化，先使用 Fake 设置仓库 | 可离线运行的应用外壳、核心 Widget 测试 | 启动失败可恢复；中英文和三种主题模式可切换；导航栈保持稳定；默认无外部请求 |
| **Phase 3：设置持久化** | 打通可复用的设置链路 | 实现偏好适配器、设置读取和写入；落实 FIFO 队列及失败结果；验证容器销毁、写入排空与重建屏障 | 设置模块、并发与失败测试、Android 重启验证记录 | 主题和语言跨重启恢复；坏值和读取失败可降级；连续写入不覆盖；失败不显示成功；旧写入不会造成新状态回退 |
| **Phase 4：网络与通用组件** | 提供业务开发的最小示范 | 实现 Dio 配置、取消和错误映射；建立 Fake/API Repository 示例；实现加载、空、错误和重试组件；接入应用信息、外链和安全日志 | 可替换的数据访问示例、通用状态组件、平台适配器 | Fake 默认离线运行；API 配置校验明确；错误及取消行为可测；默认无自动重试；模板控制的日志路径无敏感原文 |
| **Phase 5：质量与平台验收** | 形成团队可依赖的开发底座 | 补齐关键行为测试；完善翻译检查与 CI 门禁；执行 Android 启动、返回、系统主题/语言、大字体、外链失败及重启检查 | 完整 CI、平台验收清单、结果与限制报告 | 关键失败路径和平台行为通过验证；CI 能阻止已定义的不合格变更；未覆盖项明确可追溯 |
| **Phase 6：模板化与首版发布** | 证明模板能够用于创建新 App | 实现实例化脚本或 workflow；替换包名、原生标识和品牌；检查残留；从模板生成独立示例 App；完善 README、扩展指南和版本记录 | 模板 v1.0、实例化工具、独立示例 App、使用与升级说明 | 一条命令或 workflow 完成实例化；新 App 通过 Android 构建；能按说明新增业务页面和替换数据源；无未获准的模板标识残留 |

## 5. 实施约定

### 5.1 优先验证复杂契约

Phase 3 先用可控 Fake 验证设置队列与重建时序，再接入真实存储插件。若实现明显过重，及时简化设计并同步开发说明；不能通过省略失败路径或放弃验证来宣告完成。

启动超时、迟到结果、资源回收、设置写入失败及容器重建的行为，以开发说明中的契约为准；本计划中的摘要不替代详细定义。

### 5.2 保持首版范围稳定

认证、支付、推送、数据库、WebView 等继续作为按需模块，不纳入首版默认交付。新增默认能力应有跨项目复用依据，并明确对实现、依赖和验收的影响。

### 5.3 如实记录平台限制

iOS 验证为可选项，不阻塞阶段完成或推进；未执行时标记“未验证”，不得据此声称 iOS 通过。Android 运行与重启验收不能用单元测试、Fake 或构建替代。发布模式、签名及真实插件行为各自记录，不从 debug/Simulator 编译成功推断。

### 5.4 区分模板发布与应用上架

模板 v1.0 不要求携带真实签名、生产服务或商店账号。首版交付需包含发布构建与签名说明、可用环境下的验证记录和待执行项；派生应用另行完成开发说明规定的发布就绪验收。

### 5.5 持续维护文档与证据

工具链、依赖、接口、目录或运行方式发生变化时，同步更新开发说明、README、测试及 CI。每项验证记录至少包含代码版本、命令、工具链、设备/系统（适用时）、实际结果和证据位置。

## 6. 最终使用验收

安排一位未参与模板实现的开发人员，仅依据 README 完成以下流程：

1. 从明确的模板版本创建独立 App。
2. 替换应用标识、名称和品牌资源。
3. 新增一个业务页面并接入路由和本地化文案。
4. 按示例替换或新增数据源，保持默认测试可离线执行。
5. 运行质量检查，并完成 Android 构建及必要的运行验证。

记录所需人工操作、文档缺失、阻塞问题及修复结果。该流程用于验证模板是否实现“减少从零搭建、统一团队底座”的目标；不能仅以模板自身能够启动作为最终验收依据。
