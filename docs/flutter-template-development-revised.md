## 1. 项目目标与原则

### 1.1 项目定位

本文用于指导开发一个可复用的 Flutter 空壳应用模板，并以该模板统一团队的 Flutter 开发底座。开发人员从模板创建各类 Flutter App 时，可以直接沿用已经验证的基础能力、工程结构和开发约定，集中精力实现业务，减少每个项目从零搭建和重复选型的工作。首版支持 Android 和 iOS，其他 Flutter 平台按后续需求扩展。

本文、模板和派生应用的关系如下：

| 对象 | 职责与交付 |
| --- | --- |
| 开发说明 | 规定模板的能力范围、技术契约、实现约定与验收标准，指导模板开发和维护。 |
| 空壳应用模板 | 提供可运行的工程源码、通用基础能力、最小示例、测试、CI 与使用说明，作为团队创建应用的统一起点。 |
| 派生应用 | 从模板创建独立应用，替换品牌及应用标识，按需接入业务页面、后端和平台模块，并独立维护发布。 |

团队统一的内容包括工具链与依赖基线、目录与命名、状态和依赖注入、路由、主题与国际化、网络与存储边界、错误日志、测试和构建门禁。模板同时提供明确的替换与扩展入口，品牌、业务模型、业务流程和具体服务由派生应用决定。新增通用能力应有跨项目复用依据，单个应用的业务代码留在该应用中。

模板应能独立启动，提供一个简洁的首页和设置页，用来展示基础能力；这些页面不依赖真实业务后端。网络能力提供可替换的数据源和演示入口，默认启动不请求外部服务。

### 1.2 设计原则

1. **默认可运行**：获取依赖并完成平台环境配置后，可以直接运行；不要求填写第三方账号、证书密钥或业务 API 地址。
2. **通用能力优先**：默认实现多数应用都会使用的基础设施；平台集成和有明确业务前提的能力按需添加。
3. **简单且可扩展**：按功能组织代码，以清晰边界替代复杂继承体系。只有出现实际复杂度时才增加抽象或独立领域层。
4. **可替换、可测试**：通过构造参数和 Riverpod 注入依赖；外部服务、存储和时钟等边界允许使用测试实现。
5. **平台行为透明**：说明每项能力的平台支持、权限和失败处理，避免在界面中假设所有平台行为一致。
6. **安全默认值**：不提交真实密钥；日志不记录密码、令牌和敏感请求内容；示例配置不能误指向生产环境。
7. **依赖有明确用途**：优先使用 Flutter/Dart 自带能力；引入插件前确认所支持的平台、维护状态、许可证和 SDK 约束。
8. **团队底座一致**：新应用采用模板已验证的工程约定；项目确需偏离时，记录原因、替代方案与验证结果。共性改进回馈模板，经评审和验证后供后续项目采用。

| 环境配置 | 区分开发、测试、生产环境，配置通过统一入口读取 | 提供示例值；配置文件和客户端产物均不作为密钥保险箱。 |

| 网络基础设施 | HTTP 客户端配置、超时、取消、错误映射和 Repository 示例 | 默认使用本地 Fake 演示数据；不预设服务端返回格式或认证协议。 |

| 日志与错误 | 开发日志、Flutter/异步错误入口和脱敏约定 | 默认本地输出；线上采集服务按需接入。 |
| 应用信息和外链 | 展示应用版本，打开外部链接并处理失败 | 只在需要时触发系统能力；演示链接可由派生项目替换。 |

### 2.2 按需模块

| 能力 | 推荐方向 | 延后原因与接入前提 |

### 2.3 首版不交付的业务功能

用户注册、真实登录、支付、购物、社交、广告、业务统计和具体后端接口均由派生项目实现。模板可以展示接口边界和模拟状态，但不模拟完整业务流程。

## 3. 技术选型与依赖

### 3.1 架构与基础依赖决策

| 关注点 | 首版选择 | 选择理由与适用边界 |
| --- | --- | --- |
| UI | Flutter Material 3 | 使用 SDK 自带组件和主题，减少基础 UI 依赖。 |
| 状态管理与依赖注入 | [`flutter_riverpod`](https://pub.dev/packages/flutter_riverpod) | 按用户期望采用 Riverpod；使用 Provider 表达依赖、Notifier 表达可变状态。Flutter 官方架构文档推荐 `provider` 作为依赖注入方案，Riverpod 是本项目的替代选择，并非 Flutter 官方唯一推荐。 |
| Riverpod 代码生成 | 首版手写 Provider | 状态规模较小时降低生成工具链成本；需要生成式 API 时再评估 `riverpod_generator`。 |
| 路由 | [`go_router`](https://pub.dev/packages/go_router) | 声明式路由，适用于深度链接和嵌套导航；简单临时页面可使用 Flutter Navigator。 |
| 国际化 | Flutter `flutter_localizations`、`gen_l10n`、[`intl`](https://pub.dev/packages/intl) | SDK 支持 ARB、生成的类型化访问接口及日期/数字格式化。 |
| HTTP | [`dio`](https://pub.dev/packages/dio) | 统一超时、拦截器、取消和上传下载能力；接口应避免将 Dio 类型扩散到展示层。 |
| 简单偏好 | [`shared_preferences`](https://pub.dev/packages/shared_preferences) | 保存主题和语言等非敏感小型键值数据；不当作数据库或安全存储。 |
| 包信息 | [`package_info_plus`](https://pub.dev/packages/package_info_plus) | 获取应用名称、版本与构建号。 |
| 外链 | [`url_launcher`](https://pub.dev/packages/url_launcher) | 使用平台支持的方式打开 URL；处理失败和平台配置差异。 |
| 静态检查 | [`flutter_lints`](https://pub.dev/packages/flutter_lints) | 作为基础规则，项目根据需要增补，规则变更纳入代码审查。 |
| 测试 | Flutter SDK 的 `flutter_test`，按需选择额外工具 | 优先使用可替换依赖与 Fake；以行为和边界为测试目标。 |

Flutter 官方推荐明确分离 UI 和数据层，使用 Repository 与依赖注入，并推荐 `go_router`；同时指出更复杂的领域层应视项目需要引入。[Flutter 架构建议](https://docs.flutter.dev/app-architecture/recommendations) Flutter 官方国际化流程使用 ARB 和 `gen_l10n`。[Flutter 国际化指南](https://docs.flutter.dev/ui/internationalization)

### 3.2 版本与生成文件管理

- 模板是应用工程：实施时将 Flutter SDK 版本记录在团队约定的版本管理配置中，并提交 `pubspec.lock`，使开发和 CI 解析到一致依赖。
- `pubspec.yaml` 使用经过双平台构建验证的兼容约束，不盲目使用任意版本，也不对未验证的最新版本作保证。
- 定期执行依赖过期和许可证检查；升级时先阅读破坏性变更与平台最低版本要求，再更新锁文件。
- 本地化生成源文件的位置及是否提交生成产物，在后续国际化章节统一确定；无论采用哪种策略，都要保证干净检出后可以按文档生成和构建。
- 不默认引入模型生成工具；当不可变模型或 JSON 模型的重复代码足够多时，再评估 `freezed`、`json_serializable` 和构建时间成本。

### 3.3 新增依赖的审查清单

1. 用一句话说明功能需求，以及 Flutter/Dart 自带 API 是否足够。
2. 查看维护状态、发布记录、问题处理情况和许可证。
3. 核对 Android、iOS 平台支持，Flutter/Dart 和原生最低版本。
4. 明确权限、原生配置、网络请求、隐私影响和失败行为。
5. 对比替代方案与移除成本；将插件限制在服务或适配层内。
6. 更新依赖锁定、平台构建验证及相关说明。

## 4. 项目目录与分层

以下为拟议结构，目录仅在对应文件存在时创建。具体文件名可随实现调整，但职责和依赖方向应保持一致。

```text
lib/
  main.dart                    # 入口与启动协调
  app/
    app.dart                   # 应用根组件
    config/                    # 环境和应用配置
    router/                    # go_router 配置
    theme/                     # 主题与设计令牌
  core/
    error/                     # 通用错误类型与映射
    logging/                   # 日志接口与实现
    network/                   # HTTP 客户端与通用拦截器
    storage/                   # 持久化抽象和适配器
    ui/                        # 通用组件：加载、空状态、错误
  features/
    home/
      presentation/            # 首页、页面状态和交互
    settings/
      data/                    # 设置存储实现
      domain/                  # 设置模型与必要接口
      presentation/            # 设置页及其状态
  l10n/                        # ARB 与约定的生成输出
assets/
  images/
  fonts/
test/
  core/
  features/
integration_test/              # 按需添加的平台集成测试
docs/                          # 设计、配置与开发说明
```

### 4.1 层次职责

- **Presentation**：Widget 负责布局、显示状态和收集用户操作；Riverpod Notifier/Provider 负责组织页面状态及调用数据层。纯局部动画和输入框状态可以留在 Widget 内。
- **Data**：Repository 负责组织和提供应用数据，Service/数据源封装 HTTP、偏好存储等外部访问；数据源不直接操作页面。
- **Domain（按需）**：放置被多个层次共享的领域模型、接口和确有必要的业务规则。对于简单设置功能，可以保留小型模型；不要求每个功能都建立完整 domain 目录或 use case。
- **App**：组合根组件、路由、主题和环境；不要把具体页面逻辑堆在入口文件。
- **Core**：只放跨功能复用且职责稳定的基础能力；某个功能专属代码留在对应 feature，避免把 `core` 变成杂物目录。

### 4.2 依赖方向

```text
Widget / 页面 → Provider / Notifier → Repository 接口 → 数据源接口
                                          ↑                  ↑
                                   Repository 实现       HTTP / 本地存储实现
```

应用组合层负责通过 Riverpod 绑定接口与实现。页面不直接访问 Dio、插件单例或具体存储实现；底层数据源不依赖页面、路由或 `BuildContext`。简单功能不必为了套用图示而创建只有一行转发的多层类；当需要替换、隔离副作用或复用时再引入相应边界。

### 4.3 命名与资源约定

- 文件和目录使用 `snake_case`；类型使用 `UpperCamelCase`；变量和方法使用 `lowerCamelCase`。
- 页面、状态对象、仓库和数据源采用能说明职责的名字，例如 `SettingsScreen`、`SettingsNotifier`、`SettingsRepository`。
- 用户可见文案进入 ARB；调试日志不当作用户提示。
- 图片和字体统一声明并集中管理；避免在多个页面硬编码资源路径。
- 平台专属代码封装在明确的适配边界内，调用方处理不可用或失败结果。

## 5. 启动流程与环境配置

### 5.1 启动目标和顺序

首版将语言和主题等偏好读取纳入主应用首帧前初始化，避免主页面显示默认外观后再闪变。进程先显示不依赖设置的中性启动视图；它不是主题/语言已经初始化的业务首屏。网络客户端和路由的依赖应可同步构造；首屏不等待服务器、第三方统计服务或更新检查。

1. 在 `main` 中调用 `WidgetsFlutterBinding.ensureInitialized()`。
2. 安装 Flutter 框架错误和主 isolate 未捕获异步错误的安全处理入口；原始异常与堆栈仅留在受控诊断边界，不直接输出。
3. 仅调用一次 `runApp(StartupCoordinatorApp(...))`，由稳定的协调器开始初始化。
4. 读取并校验构建环境配置；配置不合法视为启动失败，不自动指向生产环境。
5. 初始化非敏感偏好存储，读取、校验并规范化设置快照。
6. 构造依赖，成功后将环境、已初始化的设置仓库和设置快照通过 `ProviderScope` 注入；应用根组件构建 `MaterialApp.router`。

读取设置失败时，不覆盖原始持久化数据：记录错误，并以跟随系统的默认设置启动；后续保存成功后再更新存储。若环境配置无效或关键依赖无法创建，则显示独立的启动失败界面，提供重试或退出当前流程；不可悄悄切换生产配置。启动失败界面使用本地、无外部服务依赖的基础文案和 Material 组件，不依赖尚未完成初始化的路由或设置 Provider。

启动阶段捕获可恢复异常后要保留受控诊断信息并展示可理解的错误；全局处理器是兜底，不能代替操作自身的错误处理。`FlutterError.onError` 按第 13.2 节先构造安全诊断，Debug 下仅以脱敏后的 `FlutterErrorDetails` 调用 `FlutterError.presentError`，Profile/Release 仅输出允许列表字段；不得先输出原始错误再脱敏。`PlatformDispatcher.instance.onError` 返回 `true` 表示应用已处理该异常。该入口不能自动捕获其他 isolate 的所有错误，派生项目使用 isolate 时应单独转发。参考 [Flutter 错误处理文档](https://docs.flutter.dev/testing/errors)。

默认不使用自定义 Zone 收集日志。如果后续插件要求 Zone，必须保证绑定初始化和 `runApp` 处于同一 Zone，见 [Flutter Zone 说明](https://docs.flutter.dev/release/breaking-changes/zone-errors)。不在 `initState` 里直接依赖尚未挂载完成的页面上下文显示弹窗；需要展示的启动提示在首帧之后且确认组件仍挂载时触发。

### 5.2 环境定义与配置

首版定义 `development`、`staging`、`production` 三种逻辑环境，由 `--dart-define=APP_ENV=...` 选择；本地未传入时使用 `development`。未知值报配置错误，禁止回退到生产环境。用统一的不可变 `AppConfig` 暴露环境名称、API base URI 和功能开关；调用方通过 Provider 读取，不在页面中直接读取编译变量。

```bash
flutter run --dart-define=APP_ENV=development
flutter run --dart-define=APP_ENV=staging
flutter build apk --release --dart-define=APP_ENV=production
```

上述命令只选择 Dart 层配置，不自动创建 Android product flavors、iOS schemes，也不改变 application ID 或签名。需要并行安装不同环境时，按第 15.4 节增加原生配置。默认 `dataSourceMode=fake`、API base URI 为 `null`，三种环境均可离线启动；Fake 模式不得创建发请求的后台任务。显式选择 API 模式时，必须提供合法且符合环境策略的 HTTPS base URI，缺失或占位地址视为配置错误，不回退到其他服务。开发环境如需本机 HTTP 调试，由派生项目显式配置平台例外。

构建变量固定为 `APP_ENV`（默认 `development`）、`DATA_SOURCE_MODE`（`fake` / `api`，默认 `fake`）和 `API_BASE_URI`（默认空字符串，解析为 `null`）。未知模式报配置错误；API 模式示例为 `--dart-define=DATA_SOURCE_MODE=api --dart-define=API_BASE_URI=https://<实际服务域名>/`，此处地址仅为说明，不能直接使用。Fake 模式若传入非空 API 地址也报配置错误，避免配置被静默忽略。实现和 README 须使用同一组名称与规则。

`--dart-define` 和客户端资源可能被提取，不能用于保存服务端私钥或其他必须保密的凭据。构建时固定的公开配置可以通过此方式注入；用户令牌的存储与安全策略见第 11.3 节。

### 5.3 启动伪代码与验收

以下仅展示组合方式，`Bootstrap`、`StartupCoordinatorApp` 和相关状态均是待实现的应用类型，不是 Flutter SDK 自带 API；具体状态切换、截止时间和资源清理由第 5.4 节约束：

```dart
void main() {
  WidgetsFlutterBinding.ensureInitialized();
  installGlobalErrorHandlers();
  runApp(StartupCoordinatorApp(
    load: Bootstrap.loadFromEnvironment,
  ));
}
```

协调器在 `initializing` 显示中性启动视图；在 `ready` 挂载一个稳定的 `ProviderScope(retry: (count, error) => null, ...)` 和主应用；在 `failed` 显示安全类别及重试按钮。加载函数解析环境并区分可降级的偏好读取错误和不可恢复的配置/依赖错误。重试通过协调器状态转换重新执行加载，不调用 `main` 或 `runApp`。错误处理器只在入口安装一次。

**验收**：首次安装、已有设置重启、偏好存储不可用、错误环境值及离线启动均有确定行为；启动过程不发外部请求，也不存在主题或语言先显示默认值再跳变。

### 5.4 启动状态机、重试和资源所有权

启动协调器由入口层唯一持有，状态为 `initializing → ready | failed`；`failed → initializing` 仅由用户重试触发。整个进程仅在入口调用一次 `runApp`，不递归调用 `main()`。主题、语言变化不重新创建协调器、应用容器或路由器。

初始化拆成可逆步骤并维护已创建资源栈（例如存储适配器、Dio、监听器）。任一步失败，按逆序释放已创建资源；释放过程幂等。重试按钮有 in-flight 锁，双击只触发一次初始化。初始化成功后资源所有权转移到应用容器，失败视图不能持有这些资源。偏好读取失败属于可降级项，环境解析和必要依赖构造失败属于失败页；失败信息提供安全类别和重试动作，不显示原始异常。

**等待预算**：首版偏好初始化/读取预算合计 2 秒，每次完整初始化预算 5 秒，使用可注入时钟测试；这些是初始产品约定，后续依据双平台实测调整。偏好超时与读取失败相同，使用默认快照继续，不写回默认值；完整初始化超时进入失败页。同步阻塞无法由 Future 超时打断，禁止在主 isolate 执行长耗时同步初始化。

Future 超时不代表底层操作已取消。每次尝试分配独立身份和资源栈；超时后使其失效，尽力取消可取消操作，迟到结果不能替换当前状态或设置快照，其资源由旧尝试自行释放。超时任务的迟到异常必须被接收并安全记录。尚未结束且不能隔离的插件初始化不得再次并发执行，重试按钮应说明需等待或重启应用；不能仅以 `Future.timeout` 启动重复原生初始化。偏好读取超时只接受迟到结果的清理，不接受其覆盖已经显示或修改的设置。

**验收**：用可控 Bootstrap Fake 注入每个步骤失败、永久等待、迟到成功和迟到异常，验证截止时间、清理顺序、幂等清理、连续重试、双击防重及尝试间隔离；成功只构造一个路由器/容器；启动失败视图在 ProviderScope 不存在时仍可渲染。

## 6. 路由与页面组织

### 6.1 首版路由表

应用使用 `MaterialApp.router` 和单个生命周期稳定的 `GoRouter`。以下是首版约定；路径常量集中维护，避免页面散落字符串。

| 路径 | 页面 | 访问规则 |
| --- | --- | --- |
| `/` | 首页 | 公开，默认入口。 |
| `/settings` | 设置 | 公开，从首页进入。 |
| 其他未知路径 | 未找到页面 | 显示本地化提示和返回首页入口，不抛出未处理异常。 |

首版没有登录状态和受保护页面，也不安装身份验证插件。日后需要登录时，在路由组合层增加会话状态与重定向规则，并区分会话加载中、已登录和未登录；不得把登录页与目标页互相重定向造成循环。外部深度链接涉及关联域名、平台声明和启动恢复，只有配置并验证后才能宣称支持。

### 6.2 导航语义与参数

- `context.go(...)` 用于切换应用当前位置，例如回到首页；`context.push(...)` 用于在当前页面上打开设置等可返回页面。不要把两者当作同义词；结合真实返回栈设计页面流程。
- 返回上一页优先使用 `context.pop()`；弹窗和局部临时页面可使用 Flutter Navigator。返回前确认存在可返回页面，深度链接直接进入的页面应提供回到首页的退路。
- 可通过链接恢复的标识使用 path/query 参数；使用 `Uri` 或 `goNamed` 的参数构建 URL，不手工拼接转义。参数须在目标页面解析和校验，不可信参数不得直接作为任意 WebView 地址或外部跳转目标。
- `extra` 只传递当前导航过程可用的临时对象，不能假定进程重启或外部深度链接后仍存在；关键页面标识和恢复所需信息放在 URL 或持久数据中。
- 返回拦截采用与 Router 配合的 `PopScope`；不要沿用旧模板的 `WillPopScope` 导航实现。先明确手势返回和有未保存内容时的用户体验。

首页与设置页的层级、`go`/`push` 的返回效果、未知路径、参数缺失以及从外部打开页面后的返回行为应在实现时逐项验证。`go_router` 关于导航与返回栈的具体行为以所锁版本的[导航文档](https://pub.dev/documentation/go_router/latest/topics/Navigation-topic.html)为准。

### 6.3 生命周期和路由状态

在应用范围创建一次路由配置，设置主题或语言时不重新创建 `GoRouter`，防止导航栈被重置。路由资源在其拥有者销毁时清理；初版不建立全局静态导航单例。以后接入认证监听时，应通过稳定的监听桥接触发重定向刷新，并定义监听订阅的释放方式。

**验收**：从首页进入设置并返回后首页仍正常；切换语言/主题后当前页面和导航栈保留；未知路径有可恢复界面。

## 7. Riverpod 状态与依赖注入

### 7.1 状态归属

| 状态或依赖 | 放置位置 | 生命周期与用途 |
| --- | --- | --- |
| `AppConfig` | 普通 `Provider` | 应用级不可变配置，在启动时注入。 |
| 设置仓库 | 普通 `Provider` | 应用级依赖，封装偏好读取和写入。 |
| 主题模式、语言选择 | 一个不可变 `SettingsState` + `NotifierProvider` | 应用级状态；初始快照来自启动阶段，修改后持久化。 |
| 页面加载的数据 | `FutureProvider` 或 `AsyncNotifierProvider` | 需要异步读取和展示加载、错误时使用，按页面/功能确定生命周期。 |
| 表单输入、动画、展开状态 | Widget 本地状态 | 没有跨页面共享或持久化需求时使用 `StatefulWidget` 等 SDK 能力。 |

页面用 `ref.watch` 订阅渲染所需的状态，用 `ref.read` 在点击等事件中调用动作；需要监听一次性变化时使用 `ref.listen`，避免在 `build` 中直接发请求或弹窗。Provider 之间通过 `ref.watch` 声明依赖；不要在业务服务内部持有 `BuildContext`。

### 7.2 设置状态与并发约定

`SettingsState` 包含 `ThemeMode themeMode` 和 `Locale? locale`；`null` 表示跟随系统。状态对象不可变，更新时产生新对象；允许选择的语言由应用支持列表决定，不接受任意持久化字符串。

启动时读取一次仓库并注入快照，Notifier 以该快照初始化，确保首帧状态与已保存值一致。每次修改采用以下约定：

1. UI 调用 `setThemeMode` 或 `setLocale`；Notifier 先校验输入。
2. **先保存，后更新状态**：持久化成功才发布新状态；失败时保留旧值，将可展示的错误返回给页面。
3. 设置命令通过唯一的应用级队列按提交顺序串行执行；每次写入只更新对应键，避免主题和语言同时修改时互相覆盖。后续操作基于最新已提交状态合并。
4. UI 在保存期间禁用对应设置项或显示轻量进度，失败时显示本地化提示。多次快速操作仍由应用级命令队列保证顺序，不依赖 UI 禁用作为唯一保护。
5. 损坏或未知的持久化值映射为跟随系统，并记录不包含敏感内容的诊断；不因单个坏值导致整个应用无法启动。

选择先保存后更新，意味着磁盘写入慢时切换不会立即生效；但用户看到的新值与持久化调用成功状态一致。精确提交顺序、写入不确定性和队列作用域按第 7.3 节执行；该机制不是关键业务数据的持久化保障。

### 7.3 异步与资源管理

**Riverpod 版本契约（首版采用 Riverpod 3.x，具体补丁版在锁文件中固定）**：Riverpod 3 的 provider 默认带有失败后的自动重试行为；不得仅凭“Dio 不自动重试”推断应用不会重复请求。首版 `ProviderScope` 全局关闭默认重试（`retry: (retryCount, error) => null`），纯查询仅在 provider 声明中显式开启有限次数、退避间隔和可重试错误类别；写操作不得自动重试。所有回调签名以锁定版 API 为准。官方说明见 [Riverpod 3.0 更新](https://riverpod.dev/docs/whats_new) 与[自动重试](https://riverpod.dev/docs/concepts2/retry)。

- provider 生命周期按实际访问模式选择：页面专属查询优先自动销毁；应用级配置、路由和设置状态由稳定的应用容器持有。使用 `keepAlive` 必须写明保留原因与失效条件，不以默认常驻解决生命周期问题。
- Provider 3 的 `Ref` 生命周期边界更严格；异步回调在 `await` 后不得假设原 `Ref` 仍有效。必要时在异步边界前捕获依赖/取消令牌，使用锁定版建议的 `Ref.mounted` 检查，并确保 disposed provider 不再发布状态。
- `ref.onDispose` 只释放本 Provider 所拥有的资源。Dio、CancelToken、StreamSubscription、Timer 和监听桥接均须标明创建者、所有者及关闭责任；共享客户端不能由页面 Provider 关闭。
- 查询请求取消和结果过期保护分开定义：取消是资源优化，序列号/请求身份校验负责阻止旧响应覆盖新状态。取消错误作为正常结束处理。

**设置写入的确定性提交协议**：`SettingsNotifier` 是当前一代应用设置的唯一内存状态所有者。应用资源所有者持有一个 `SettingsCommandQueue`，其生命周期跨越 Notifier 的销毁与重建；队列只维护任务顺序、代次和完成屏障，不持有设置副本。Repository 只做逐键读写，不另建队列或可变设置缓存。所有写入必须经由 Notifier 提交到此队列，禁止页面或其他 Provider 绕过队列写仓库。

每个命令从入队到返回都有明确结果；队列中的一次完整任务依次执行：校验参数和代次 → 读取当前 Notifier 最新已提交状态 → 只修改目标键得到候选状态 → 等待 Repository 写入对应键 → 成功后同步发布候选状态 → 完成本次调用。下一任务只能在前一任务完成提交或失败处理后开始；同键命令不合并，两键共用一个 FIFO。前一任务失败不阻断后续任务，队列尾部异常必须吸收，失败归属当前调用。A 成功、B 失败时保留 A 的已提交状态。

**分层失败风格**：存储适配器/Repository 的读取和写入均通过 `Future` 返回数据或抛出 `AppException`，写入失败类别为 `storageWrite`。Notifier 在队列任务边界捕获预期的 `AppException` 并返回 `SettingsWriteFailure`；成功返回 `SettingsWriteSuccess`。不捕获并伪装编程 `Error`；队列须让该任务异常完成、释放占用并保持后续任务可执行，UI 调用入口将非预期异常交给统一错误边界，不能遗留未处理 Future。UI 对预期失败只消费封闭结果，不接触插件异常。

```dart
abstract interface class SettingsRepository {
  Future<SettingsState> read(); // 返回规范化快照；预期失败抛 AppException
  Future<void> writeThemeMode(ThemeMode value); // 预期失败抛 AppException
  Future<void> writeLocale(Locale? value); // null 表示 system；预期失败抛 AppException
}

class SettingsState {
  const SettingsState({required this.themeMode, required this.locale});
  final ThemeMode themeMode;
  final Locale? locale;
}

sealed class SettingsWriteResult {
  const SettingsWriteResult();
}
final class SettingsWriteSuccess extends SettingsWriteResult {
  const SettingsWriteSuccess(this.state);
  final SettingsState state;
}
final class SettingsWriteFailure extends SettingsWriteResult {
  const SettingsWriteFailure(this.failure);
  final AppFailure failure;
}
```

`SettingsState` 同时作为仓库读取的不可变快照和 Notifier 状态，不另设未定义的 `SettingsSnapshot`。完整实现须提供值比较及不可变复制方法。

**销毁与重建屏障**：普通页面退出不销毁应用级设置 Notifier，也不取消已接受的命令。需要主动重建应用容器时，应用资源所有者先关闭旧代次的命令入口，让已接受的任务排空，再销毁旧 Notifier；禁止直接 invalidate 设置 Notifier 后从启动快照恢复。

若旧 Notifier 意外提前销毁，队列废弃其代次：尚未执行的命令返回 `SettingsWriteFailure(AppFailure(AppFailureKind.cancelled))`，不调用插件；已经交给插件的写入继续等待实际结果，结束后不发布到已销毁的 Notifier。此操作仍按写入实际返回值完成成功/失败结果，成功中的候选状态只代表该次操作，不能被旧 Widget 用于更新 UI；Widget 在 await 后检查 mounted。取消结果静默处理。

新一代恢复必须由应用资源所有者按顺序完成：关闭新命令入口 → 等待共享队列中旧代次的在途写入实际结束 → 通过同一仓库重新读取并规范化 → 构造新 Notifier 和注入快照 → 开放新代次命令。等待及读取期间显示恢复视图，不能先展示旧启动快照。若在途写入长期未完成，5 秒后显示安全恢复失败状态并提示重启；超时不表示写入结束，不能创建新仓库或开启新队列绕过屏障。资源所有者只在写入排空后释放仓库；正常进程终止不承诺尚未完成的写入持久化。

插件返回异常可能表示写入结果不确定；Notifier 返回 `storageWrite`，保留最近确认的内存状态并记录安全诊断，不擅自重试，不承诺磁盘与内存绝对一致。下一次启动或受控重建按屏障重新读取。该队列仅保证一个应用资源所有者、一个 isolate 内的顺序；多实例、多进程写入不在首版范围。

- 异步页面使用 `AsyncValue` 或等价状态明确表示加载、成功、空结果与失败；空结果属于成功数据的一种，不与异常混为一谈。
- 请求可重复触发时，定义取消或过期结果处理，防止旧请求覆盖新结果；页面卸载后不再使用无效 `BuildContext`。
- 网络客户端、流订阅和控制器由创建它们的 Provider 或 Widget 管理，使用 `ref.onDispose` / `dispose` 释放。对自动释放的 Provider，明确其缓存和重新加载行为。
- 启动覆盖、Fake 仓库和网络客户端通过 Provider override 注入，测试无需修改生产单例。默认不使用 `ChangeNotifierProvider` 创建新状态，也不为 Riverpod 引入第二套 Provider 状态系统。

### 7.4 Riverpod 自动重试和生命周期验收

- 用可计数 Fake 验证失败查询的重试次数、延迟/取消语义；副作用 Provider 验证失败后调用次数仍为一次。
- 验证 Provider 被销毁后取消所属请求、释放订阅，迟到结果不发布；重新进入页面时按约定重新加载或复用。
- 验证设置队列：两个不同键并发、同键快速连续修改、A 成功后 B 失败，以及失败后队列继续工作。
- 用可控 Completer 验证旧代次写入未完成时，新代次不得读取或接受命令；旧写入完成后才重读，且新状态包含该结果。覆盖主动排空、意外销毁、待执行任务取消、在途写入失败及永久等待；全部任务 Future 均须有明确归属。
- 验证跨键状态合并发生在前一任务提交之后；已销毁代次不能发布状态或使用 Widget 上下文。
- Riverpod 升级审查需核对 changelog 中重试、Ref、自动销毁和测试 API 的变化。

**验收**：主题与语言状态在不同页面一致；保存失败时 UI 不发布成功状态，实际存储结果的不确定性按上述契约处理；并发修改互不覆盖；退出页面后监听和资源能够释放。Riverpod 的具体 API 随锁定版本核对，参考 [Riverpod Provider 文档](https://riverpod.dev/docs/concepts2/providers)。

## 8. 主题、视觉规范与无障碍

### 8.1 主题模型

模板支持 `ThemeMode.system`、`ThemeMode.light`、`ThemeMode.dark`，默认跟随系统。首版不提供用户自定义主题色；品牌色由派生项目修改主题配置。使用单一品牌种子色分别生成浅色和深色 `ColorScheme`，通过 `ThemeData` 配置文字、按钮、输入框等组件；页面通过 `Theme.of(context)` 读取，避免在各页面硬编码颜色。

根组件同时设置 `theme`、`darkTheme` 和 `themeMode`。系统模式随操作系统的亮暗变化；切换语言不会修改主题选择。持久化值使用稳定字符串 `system`、`light`、`dark`，不要保存枚举索引；未知值退回 `system`。设置页以本地化名称显示选项，选择保存成功后更新当前界面。

### 8.2 视觉与资源约定

- 统一定义间距、圆角和文字层级等常用值；优先使用 Material 的语义色，如 `surface`、`onSurface`、`error`，确保亮暗主题均可阅读。
- 首页和设置页适配窄屏、横屏、系统安全区域与键盘遮挡；列表内容超过高度时允许滚动。
- 图片应有加载失败处理；有含义的图标提供语义标签，纯装饰图标从语义树排除。
- 可点击区域、文字缩放、对比度和焦点顺序应纳入页面验收。UI 不以颜色作为唯一状态标识。
- 字体和资源仅在确有需求时加入，确保许可证允许应用分发和再利用。

**验收**：三种主题模式可切换并在重启后恢复；系统模式响应系统变化；亮暗主题下首页、设置页和状态组件均保持可读；常见大字号下关键操作可见且可滚动。

## 9. 国际化与语言设置

### 9.1 资源和生成策略

使用 Flutter `gen_l10n` 生成 `AppLocalizations`，英文 ARB 作为模板资源，简体中文 ARB 提供完整翻译。目录示例：

```text
lib/l10n/
  app_en.arb
  app_zh.arb
  generated/                  # gen_l10n 输出，加入 .gitignore
l10n.yaml
```

`pubspec.yaml` 声明 `flutter_localizations`、`intl` 并设置 `flutter.generate: true`。`l10n.yaml` 指定 ARB 目录、模板文件和 `output-dir: lib/l10n/generated`；源码从项目内生成路径导入，不使用旧的 `flutter_gen` 合成包。生成文件不提交，干净检出后由 `flutter pub get` / `flutter gen-l10n` 生成；CI 在分析和构建前执行生成，确保工具链完整。生成参数以固定 Flutter 版本的 `flutter gen-l10n --help` 为准。[Flutter 生成源码迁移说明](https://docs.flutter.dev/release/breaking-changes/flutter-generate-i10n-source)

示例资源使用带类型的占位符；首版不拼接需要按语言调整语序的句子：

```json
{
  "appTitle": "Flutter Template",
  "helloUser": "Hello, {name}!",
  "@helloUser": {
    "description": "Greeting shown on the example page",
    "placeholders": {"name": {"type": "String"}}
  }
}
```

### 9.2 Locale 选择与持久化

- 设置项为“跟随系统”“简体中文”“English”，用户选择使用 `null`、`Locale('zh')`、`Locale('en')` 表示；对应存储值为 `system`、`zh`、`en`。
- `MaterialApp.router` 的 `locale` 直接读取设置状态；为 `null` 时交由 Flutter 按系统语言列表与 `supportedLocales` 解析。系统语言变化时跟随系统模式应自动更新。
- 支持的 Locale 与 delegate 使用生成的 `AppLocalizations.supportedLocales` 和 `localizationsDelegates`；英文作为不匹配时的默认回退，具体生成顺序需在配置或应用层显式保证，并验证。
- 首版仅提供一种中文资源，因此所有匹配到通用 `zh` 的中文环境都会显示简体中文；如果需要繁体或地区差异，新增 `zh_Hans`、`zh_Hant` 等资源并明确脚本及地区解析策略，而不是假设所有中文用户都使用简体。
- 语言切换与主题切换遵循第 7.2 节先保存后更新规则；未知存储值回退系统模式。

### 9.3 翻译规范与平台范围

- 所有用户可见文案、错误、空状态和无障碍标签都进入 ARB；翻译键使用稳定的 `lowerCamelCase`，对可能歧义的文案补充 `description`。
- 日期、数字、货币等使用当前 locale 格式化；复数和性别/选择语句使用 ARB 的 ICU 语法，并覆盖所有适用分支。
- 翻译资源必须与模板键一致；CI 检查缺失翻译和生成错误。不同语言的句子结构可独立调整，避免把可点击链接前后的文案简单硬编码拼接。
- Flutter 页面内文案由应用本地化控制；系统权限弹窗、应用名称和商店描述等原生文本需要分别配置平台资源，不自动由 ARB 覆盖。

**验收**：应用内中英文切换立即生效并在重启后保留；跟随系统模式响应系统变更；未知系统语言回退英文；缺失翻译在构建前可发现；大字号和不同文案长度下无关键内容溢出。

## 10. 网络与数据访问

### 10.1 职责和数据流

网络基础设施基于 Dio，首版包含可配置客户端、请求取消、错误映射和一个无需真实服务器的 Repository 示例。默认不设定业务响应外壳，例如 `{code, message, data}`，也不假设所有后端使用同一种分页协议。

```text
页面 → Notifier / Provider → Repository → API Service → Dio
                                  ↘ Fake Repository（默认演示）
```

- **API Service**：负责构造路径、查询参数和请求体，解析协议数据；Dio 异常在数据边界转换为应用可理解的失败类型。
- **Repository**：协调数据来源并向上提供稳定的数据和失败结果；缓存、刷新和业务数据的合并规则在需要时由具体 Repository 定义。
- **Notifier / 页面**：根据结果显示加载、内容、空状态或重试入口；不访问 `DioException`、HTTP 响应对象或插件类型。
- **Fake Repository**：使用内置数据，供首版界面与开发演示使用；通过 Provider override 或配置注入。它不声称模拟真实后端的认证、网络延迟或所有错误。

每个环境只暴露一个配置入口；实际服务域名由派生项目提供。客户端默认不配置固定 Cookie、通用身份头或真实认证流程。测试环境可以替换 HTTP adapter 或 Repository，不需要连接公网。

### 10.2 客户端配置与生命周期

- `AppConfig` 提供可空 base URI 和超时配置；Fake 模式下不创建 API Service 或解析占位 base URI，Dio 仅在合法 API 配置下按需由 Provider 创建，由其拥有者关闭。调用方构造相对路径，避免无意覆盖基础地址；确需绝对地址时须通过受控入口并验证 scheme/host。
- 首版建议连接超时 10 秒、接收超时 30 秒、发送超时 30 秒，作为可配置起点，并根据实际 API、上传文件及网络条件调整；超时不等同于设备离线。
- 默认仅允许 HTTPS 业务服务；本机开发 HTTP 例外应显式启用并仅限开发配置，同时满足 Android/iOS 的平台限制。
- 拦截器职责分离：公共请求标识、经脱敏的诊断和错误映射分别处理；禁止记录 Authorization、Cookie、请求体和完整查询参数。默认不记录响应体。
- 页面请求传递取消能力，页面或 Provider 销毁时取消自己拥有的请求；同一共享请求的取消权由 Repository 明确，避免一个页面取消其他页面正在使用的请求。
- 上下拉刷新和并发搜索需要定义结果顺序：新查询生效后，旧查询即使稍后返回也不能覆盖新数据。

### 10.3 错误模型

数据层保留原始异常和堆栈供受控诊断，但向 UI 暴露稳定的错误类别与可选的安全信息；UI 使用本地化资源映射展示文案，不直接显示服务端异常、堆栈或技术细节。

| 类别 | 常见触发 | 页面行为 |
| --- | --- | --- |
| `cancelled` | 主动取消请求 | 通常静默结束；不显示“网络错误”。 |
| `timeout` | 连接、发送或接收超时 | 提示超时并提供重试；不推断服务器未执行操作。 |
| `connection` | DNS、连接或传输失败 | 提示连接失败；允许用户重试。 |
| `unauthorized` / `forbidden` | HTTP 401 / 403 | 首版展示通用访问失败；接入认证后再定义会话恢复和权限提示。 |
| `notFound` | HTTP 404 | 根据页面语义显示资源不存在或错误状态。 |
| `rateLimited` | HTTP 429 | 提示稍后再试；如服务端提供可信的重试时间，可按具体协议处理。 |
| `server` | HTTP 5xx | 提示服务暂不可用；保留安全的状态码用于诊断。 |
| `invalidResponse` | JSON 格式、类型或必需字段不符合约定 | 显示通用错误并记录脱敏诊断；不把解析异常伪装成空数据。 |
| `unknown` | 未覆盖的异常 | 显示通用错误并记录异常及堆栈。 |

上述 HTTP 分类属于模板的基础映射；服务端以 HTTP 200 返回业务失败时，由对应 API Service/Repository 按真实协议识别，不能在通用拦截器中猜测。服务端可读文案是否允许展示，也必须由具体接口约定。

### 10.4 分层错误契约与边界类型

**分层错误契约**：API Service/存储适配器在外部边界把预期失败转换为 `AppException`，Repository 继续传播或按真实业务协议转换，已是应用异常时不得重复包装。查询 Provider 将该失败映射为 `AsyncValue`；命令 Notifier 捕获预期的应用异常并向 UI 返回明确的封闭结果，例如 `SettingsWriteResult`。Repository 写入 API 仍为 `Future<void>`，失败通过异常表达；“写操作返回结果”特指 Notifier 面向 UI 的边界。首版不建立自定义 Result 泛型框架，至少定义下列边界类型：

```dart
enum AppFailureKind {
  cancelled, timeout, connection, unauthorized, forbidden, notFound,
  rateLimited, server, invalidResponse, storageRead, storageWrite, unknown,
}

class AppFailure {
  const AppFailure(this.kind, {this.safeCode});
  final AppFailureKind kind;
  final String? safeCode; // 只放白名单诊断码，不放 URL、响应体或用户输入
}

class AppException implements Exception {
  const AppException(this.failure, {this.cause, this.stackTrace});
  final AppFailure failure;
  final Object? cause;
  final StackTrace? stackTrace;
}
```

API Service 将 `DioException`、解析错误映射到 `AppException`；Repository 可依据业务协议把它们映射为稳定的应用失败，但展示层不得依赖 Dio 类型。`cancelled` 对查询通常静默处理。UI 文案只根据 `AppFailureKind` 本地化生成，绝不直接展示 `cause`、服务端 message 或堆栈。异常应只在一个边界完成转换，避免重复包装导致诊断丢失。

### 10.5 重试、认证与传输扩展

- **首版不自动重试**：超时和断连不能证明服务器没有执行写操作。用户可主动重试安全的查询；写操作的重试与幂等键、请求体重放、服务端行为一起设计。
- 接入认证后，按服务端协议实现令牌注入、并发刷新协调、刷新失败和登出；避免每个并发请求各自刷新，并避免刷新接口触发自身递归。登出或切换账号时，失效旧请求/刷新结果，避免过期结果恢复旧会话。
- 不因重试而自动重放上传流或非幂等请求。文件上传、下载需按功能设计进度、取消、大小限制、临时文件清理和失败恢复。
- 不通过简单的“是否连接 Wi-Fi/蜂窝网络”判断服务一定可用；实际请求结果才反映目标服务是否可达。

**验收**：Fake 模式可离线启动并展示数据；错误分类和取消行为可由替换数据源验证；超时及服务器错误不会泄露堆栈或敏感内容；默认无自动重试或后台外网请求。Dio 功能参考 [Dio 官方包文档](https://pub.dev/packages/dio)。

## 11. 本地存储与安全

### 11.1 数据分类

| 数据 | 首选位置 | 生命周期与约束 |
| --- | --- | --- |
| 主题、语言 | `shared_preferences` | 非敏感、小规模配置；卸载、系统清理或平台备份行为依平台而异。 |
| 临时文件、可重新下载缓存 | 应用缓存目录 | 系统可能随时清理；不可作为唯一数据来源。 |
| 用户需要长期保留的文件 | 应用文档目录或用户选择的位置 | 明确权限、备份、导出和删除策略。 |
| Token 等敏感凭据（按需） | 平台安全存储适配器 | 首版不保存；引入登录时评估 Keychain/Android 密钥及平台配置。 |
| 可查询、可迁移的结构化数据 | 按需选择数据库 | 数据量、事务、离线与迁移需求明确后选型。 |

`shared_preferences` 不保证写入完成即已安全落盘，不适合保存关键业务数据。第 7.2 节的“保存成功”指插件写入调用成功返回，再发布新状态；它不能保证断电、系统终止或设备故障后绝对持久。平台可能备份偏好设置，不应把“非敏感”理解为“只存在于本机且永久保留”。参考 [`shared_preferences` 文档](https://pub.dev/packages/shared_preferences)。

### 11.2 设置仓库与键规范

设置仓库读写 API 和失败语义遵循第 7.3 节：Repository 不持队列，只抛出类型化 `AppException`；应用资源所有者持有唯一 FIFO 命令队列，串行化写入及 Notifier 状态提交。Notifier 将预期存储写入异常转换为 `storageWrite` 失败结果，并保持最近一次已确认快照。不要在发生写入异常时擅自重试，因为平台调用结果可能不确定；用户可在看到失败后再次操作。队列必须测试执行顺序和前一操作失败后后续操作仍能继续（队列尾部错误需被吸收，失败只归属当前任务）。

### 11.2.1 设置键和迁移规范

首版偏好适配器优先评估 `SharedPreferencesAsync`：读写均通过异步 API 访问平台存储，避免把插件本地缓存当成多实例、多 isolate 的同步机制。应用设置只在主 isolate 统一写入，应用级命令队列保证当前资源所有者范围内的提交顺序；它不提供跨进程事务或多个实例之间的互斥。

| 键 | 值 | 默认值 |
| --- | --- | --- |
| `settings.theme_mode` | `system` / `light` / `dark` | `system` |
| `settings.locale` | `system` / `zh` / `en` | `system` |

启动时逐键解析：缺失、类型错误或未知枚举值都只使对应项回退默认值，不删除其他有效设置。若底层读取调用本身失败，按第 5.1 节使用默认快照启动并记录错误。写入单个设置时仅更新所属键；预期存储异常由仓库抛出，Notifier 转为失败结果，不发布假成功。不要提供无范围约束的“清除全部偏好”作为登出实现。

将来修改键名或数据格式时，在新版本首次读取时按明确版本进行幂等迁移：先读取旧值、转换并写入新键，确认写入调用成功后再考虑移除旧键；失败保留旧数据以便下次重试。首版不预设任何既有设置键或历史数据格式；派生应用需要继承已有安装数据时，应根据其真实旧版本另行设计并验证迁移。

### 11.3 敏感信息与认证扩展

- 不把密码、Token、私钥、Cookie 或用户敏感资料写入偏好、普通日志、URL 查询参数或源码。客户端内置密钥和混淆不能保证秘密不被提取。
- 如需认证，使用可替换的凭据存储接口，并按需接入 [`flutter_secure_storage`](https://pub.dev/packages/flutter_secure_storage)。在目标设备上核查 iOS Keychain 的可访问性、卸载/重装行为，以及 Android 密钥、备份和设备迁移行为；不要假设不同系统的生命周期一致。
- 登出时取消或使旧会话请求失效，删除应用管理的凭据和该账户私有缓存，并重置会话状态；删除失败要记录并向会话层明确返回结果。令牌撤销和服务器端会话处理以真实后端协议为准。
- 安全存储降低本地明文暴露风险，不能替代服务端授权、TLS、最小权限和失效机制；丢失密钥或恢复失败时设计重新登录路径。

**验收**：缺失、无效和不可读取设置均可降级；两项设置快速交替保存不会相互覆盖；重启恢复遵循插件能力；日志和持久化检查不到示例密码或令牌。

## 12. 平台能力与常用集成

### 12.1 首版平台能力

| 能力 | 首版行为 | 边界 |
| --- | --- | --- |
| 应用信息 | 设置页或关于区域显示名称、版本、构建号；通过 `package_info_plus` 读取。 | 读取失败显示可本地化的占位文案，不阻塞启动。 |
| 外部链接 | 通过 `url_launcher` 打开预设的帮助或项目链接；无可用处理方式时提示用户。 | 使用 `Uri` 解析；对输入或重定向目标限定允许的 scheme 和域名。 |
| 系统主题与语言 | 跟随 Flutter 的系统设置变化。 | 手动选择优先；退出跟随模式后只响应用户选择。 |
| 返回与系统界面 | 尊重系统返回、状态栏、安全区域和无障碍设置。 | 不用 `exit(0)` 关闭应用；各平台返回习惯分别验证。 |

外链适配器应将成功、不可处理和异常转换为页面可处理的结果。`canLaunchUrl` 的结果会受系统查询声明等条件影响，不能把一次 `false` 当成所有打开方式均不可用；按目标平台和实际打开方式配置，见 [`url_launcher` 文档](https://pub.dev/packages/url_launcher)。对外部输入的 `http`、`https`、`mailto`、`tel` 等只按具体功能允许，不默认允许任意 scheme。

### 12.2 权限和文件：按需接入

首版不主动申请相机、相册、通知或存储权限。添加具体功能时遵循：

1. 优先使用系统选择器和目标插件已有能力，确定平台和操作是否确实需要额外权限。
2. 用户触发相关操作后解释用途并申请最小范围权限；拒绝时仍可返回，不循环弹系统请求。
3. 按平台区分拒绝、受限制、有限授权和无法再次弹窗等结果；提供适当替代路径或由用户主动打开系统设置。状态判定以所锁插件版本为准，不能依赖 Android 状态查询总能区分“从未请求”和“永久拒绝”。
4. 在 Android Manifest / iOS Info.plist 中仅声明实际使用的权限及说明，并覆盖不同系统版本的行为；不要默认依赖旧的 Android 通用存储权限。
5. 图片或文件的选择、保存和分享分别处理大小、格式、临时文件清理及用户取消；实际需要的数据不复制进日志。

如需要统一权限查询与申请，可选择 [`permission_handler`](https://pub.dev/packages/permission_handler)；某些选择器的授权模型不同，不应机械地在所有操作前申请相册或存储权限。

### 12.3 WebView、分享和应用更新：按需接入

- **WebView**：仅在确有内嵌需求时加入 `webview_flutter`。明确允许的域名和跳转规则；默认关闭不需要的 JavaScript 和原生桥接；处理加载失败、外部 scheme、页面返回和进度。涉及登录态时分别设计 WebView Cookie 与 API 客户端会话，不假定两者自动共享。平台支持与最低版本以[插件文档](https://pub.dev/packages/webview_flutter)和锁定版本为准。
- **分享**：需要时使用 `share_plus`，明确分享文本、URI 或文件；处理用户取消、目标应用不可用与临时文件生命周期。iPad 等平台需要提供合适的分享面板定位信息。
- **应用更新**：按照应用商店或企业分发渠道单独设计。版本检查、强制更新和安装包下载均依赖后端与分发策略，首版不默认接入。

**验收**：Android/iOS 上版本信息和外链失败有可理解反馈；未启用的功能不产生权限申请；按需模块接入后逐系统版本核对权限与返回行为。

## 13. 日志、错误处理与可观测性

### 13.1 事件入口和责任

| 来源 | 处理位置 | 处理方式 |
| --- | --- | --- |
| 启动过程中的可恢复失败 | Bootstrap / 对应服务 | 记录错误与堆栈，按第 5 节降级或展示失败页。 |
| Flutter 构建、布局及框架回调异常 | `FlutterError.onError` | 先生成安全诊断；Debug 仅将脱敏详情交给 `FlutterError.presentError`，Profile/Release 走允许列表日志。 |
| 主 isolate 未被其他机制处理的异步异常 | `PlatformDispatcher.instance.onError` | 记录异常和堆栈，标记已处理；不能覆盖其他 isolate 的所有错误。 |
| 网络、存储和用户操作失败 | 各 Repository / Notifier / 页面 | 转换为可处理状态或结果；按需要记录和提示。 |
| 其他 isolate 错误 | isolate 创建方 | 配置错误转发，明确端口及其生命周期。 |

预期内的取消、权限拒绝和空数据一般不计为崩溃。错误发生时由最接近操作的层决定能否恢复；全局入口只记录未处理异常，不保证应用状态仍可安全继续。避免同一异常在每一层都作为独立故障上报；使用单一责任层或事件 ID 做关联。

### 13.2 日志等级与数据最小化

| 等级 | 用途 | 默认行为 |
| --- | --- | --- |
| debug | 开发诊断、状态转换 | Debug 环境启用；Release 默认关闭。 |
| info | 无敏感信息的关键生命周期事件 | 根据环境配置输出；避免高频刷屏。 |
| warning | 已恢复或可降级的问题 | 记录安全的错误类别和上下文。 |
| error | 未恢复异常或关键操作失败 | 记录脱敏异常类别、堆栈和可关联的事件 ID。 |

统一 `AppLogger` 接口由 Provider 注入，默认输出到本地调试日志；首版无需额外日志 SDK。日志字段采用允许列表：环境、模块、操作名、错误类别、HTTP 状态码及随机请求 ID 等。默认不记录 URL 查询、请求/响应体、Header、账号标识、设备标识、密码或 Token；异常对象和堆栈也可能包含敏感文本，输出前须经过过滤，过滤器失败时只输出固定错误类别。调试日志也遵循同样的基本脱敏规则。

错误输出也属于日志边界：[`FlutterError.presentError`](https://api.flutter.dev/flutter/foundation/FlutterError/presentError.html) 默认调用 `dumpErrorToConsole`。不得将原始 `FlutterErrorDetails` 先传给默认输出再过滤。Debug 如需保留框架诊断形式，应重新构造仅含安全类别、过滤后堆栈的详情，不携带原始 exception、context 或 informationCollector；Profile/Release 不调用默认原始详情输出，仅发送允许列表字段。失败视图及 Release 错误组件使用固定安全文案。记录器自身的失败仅输出固定类别，不能递归调用错误处理器。

脱敏验收需分别检查 `AppLogger`、框架默认输出、主 isolate 兜底和错误界面：向异常消息、上下文、附加诊断及堆栈放入模拟 Token，验证所有模板控制的输出路径均无原文。仅证明 Fake logger 接收到安全字段不足以通过验收；插件自身不可控的原生日志需逐平台核查并记录限制。

### 13.3 外部观测服务：按需接入

崩溃上报、性能追踪和埋点使用单独适配器接入，首版默认关闭，不要求第三方账号。接入前由派生项目确定收集范围、用户授权、数据保留、地区及服务商配置；仅发送必要字段，不能将完整原始异常和网络内容无条件上传。

上报本身失败不能阻塞页面或触发递归错误；对重复异常、高频事件设限。是否需要调用采集 SDK 的初始化取决于用户选择和实际功能，具体同意状态、撤回与删除流程由派生应用定义。

**验收**：Flutter 错误、主 isolate 异步错误和可恢复操作错误能进入各自入口；Fake logger 可验证错误分类和去重策略；包含模拟 Token 的请求、异常和日志均不会明文输出；不配置第三方服务时应用正常运行。

## 14. 测试与质量门禁

### 14.1 测试目标与范围

测试关注模板对使用者承诺的行为，使用 Fake 或 Provider override 隔离网络、平台插件与时间等不稳定因素。默认测试不得连接真实业务服务器、使用真实账户或依赖个人签名。Flutter 将测试分为单元、Widget 和集成测试；它们的速度、平台覆盖范围和运行环境各不相同，见 [Flutter 测试概览](https://docs.flutter.dev/testing/overview)。

| 层级 | 首版必须覆盖的行为 | 运行环境 |
| --- | --- | --- |
| 单元测试 | 环境值解析及非法值；设置默认值与无效值；设置保存失败和连续写入；网络错误映射；日志脱敏。 | 本地与 CI，使用 Fake 存储、客户端或日志。 |
| Widget 测试 | 首页到设置页的导航；主题和中英文切换；加载/空状态/错误和重试；未知路由页面。 | `flutter test`；通过依赖覆盖提供可控数据。 |
| 集成测试 | Android 和 iOS 启动、设置写入、关闭后重启恢复的关键链路；外链等插件能力根据平台提供可重复的验证方式。 | 模拟器或设备；跨进程重启不能只靠一次 Widget 测试证明。 |
| 人工检查 | 跟随系统语言/亮暗模式、系统返回、大字体、外链失败和基本无障碍。 | Android 和 iOS 的目标系统版本。 |

首版应提供可运行的测试实现和说明。持久化跨重启验证可由两个阶段的设备测试或可重复的人工步骤完成；仅在同一进程读取内存缓存不能算作重启验证。平台权限、签名、真实网络与性能等不能仅凭 Fake 测试得出结论。

### 14.2 本地检查顺序

下列命令针对**依据本文实现的模板工程**，属于待实施的检查要求，不代表已有执行结果。切换到文档第 1.3 节约定的 Flutter SDK，在第 1.5 节约定的模板工程根目录执行：

```bash
flutter --version
flutter pub get
flutter gen-l10n
dart format --output=none --set-exit-if-changed lib test integration_test
flutter analyze
flutter test
```

`integration_test` 目录在添加集成测试时创建；尚未创建时格式化命令应移除该路径。使用目标设备执行集成测试，例如 `flutter test integration_test -d <device-id>`；具体脚本需说明设备、测试文件和是否清理应用数据。目录、生成文件和 `analysis_options.yaml` 的最终路径由实现与 CI 同步维护。

`flutter gen-l10n` 能报告翻译缺失，但不能只假设日志告警会导致非零退出：CI 应生成未翻译消息报告并以脚本检查各语言的未翻译列表为空；对于多余键和模板键、占位符的一致性，也提供确定会失败的检查。生成输出不提交，检查只比较受版本管理的源文件和锁文件。

### 14.3 CI 与合并门禁

默认采用 GitHub Actions；派生项目可将同等步骤迁移到其他 CI。流水线应使用固定的 Flutter 版本，并分别设置 Android 所需 JDK/SDK 与 iOS 所需 Xcode 环境。工具链版本和 runner 镜像记录在仓库配置中，升级需经过平台构建验证。

| 阶段 | 触发与执行内容 | 结果要求 |
| --- | --- | --- |
| 基础检查 | 每次变更：获取锁定依赖、生成本地化、检查翻译、格式化检查、静态分析、单元/Widget 测试。 | 任一步失败即阻止合并；获取依赖后检查锁文件未发生意外变化。 |
| Android 构建 | 每次变更：构建可供验证的 Android debug 包。 | 编译成功；不需要发布签名。 |
| iOS 构建 | 每次变更：在 macOS runner 构建 iOS Simulator 版本。 | 编译成功；Simulator 构建不需要分发证书。 |
| 平台集成 | 发布前，及影响平台能力/启动/持久化的变更：在 Android 模拟器和 iOS Simulator 执行关键集成流程。 | 记录设备与系统版本；需要重启的步骤额外执行并记录。 |
| 发布构建 | 由具有签名配置的发布流水线或维护者按第 15 节执行。 | 签名和版本核对通过后生成可分发产物。 |

CI 缓存应以 SDK 版本和锁文件计算键，缓存失效时仍可从干净环境构建。外部密钥只放 CI 的密钥管理设施，并限制访问范围；不在普通 Pull Request 中暴露签名材料。不要把覆盖率百分比作为首版唯一质量指标；应优先检查关键失败路径、平台集成与用户可见行为。

**验收**：干净检出按上述顺序可重复执行基础检查；CI 能在翻译缺失、格式错误、分析错误、关键测试失败和平台编译失败时阻止合并。另运行第 16.2 节实例化 job。首版交付需记录 Android/iOS 的执行结果与尚未覆盖的平台限制。

## 15. 构建、发布与环境隔离

### 15.1 开发环境准备

- 安装团队固定的 Flutter stable SDK，并运行 `flutter doctor` 检查必要工具；依赖版本以项目锁文件为准。
- Android 开发需配置受支持的 Android SDK、构建工具、JDK 和可用设备或模拟器；iOS 构建需 macOS、Xcode、其命令行工具和目标设备或 Simulator。
- 按所用 Flutter、Xcode 和插件文档准备 iOS 原生依赖管理工具。最低 Android/iOS 版本、Gradle、JDK 和 Xcode 版本在首次完成双平台构建后写入项目 README 或工具链配置。
- 使用模拟器验证无需发布账号；真机签名、商店上传和发布构建按各平台账户与签名要求配置。[Android 发布指南](https://docs.flutter.dev/deployment/android) · [iOS 发布指南](https://docs.flutter.dev/deployment/ios)

### 15.2 版本和标识

`pubspec.yaml` 的 `version` 采用 `版本名+构建号`，例如 `1.0.0+1`。发布流水线记录提交、构建环境、版本名与构建号；各平台的版本号映射、递增规则和商店要求在发布前核对。

Android 使用自己的 `applicationId`、显示名称和图标；iOS 设置 Bundle Identifier、Display Name、图标和 Team。应用 ID / Bundle ID 是已发布应用的身份标识，发布后更换通常意味着创建另一个应用，派生项目应在首次发布前确定。不要依赖全项目盲目替换字符串来重命名原生项目，需逐项检查 Gradle 配置、Kotlin 包路径、Xcode target 与资源。

### 15.3 构建与签名

以下命令为示例，最终以目标 SDK、签名配置和分发渠道验证结果为准：

```bash
# 开发环境；目标设备由 -d 指定
flutter run --dart-define=APP_ENV=development

# Android CI 编译检查，不代表可上架产物
flutter build apk --debug --dart-define=APP_ENV=development

# iOS Simulator 编译检查，需 macOS + Xcode
flutter build ios --simulator --debug --dart-define=APP_ENV=development

# Android 商店发布构建：先配置 release 签名
flutter build appbundle --release --dart-define=APP_ENV=production

# iOS 发布构建：先配置 Team、证书和 provisioning
flutter build ipa --release --dart-define=APP_ENV=production
```

- Android 发布签名使用项目维护者管理的 keystore 与凭据，私钥文件和密码不提交仓库；验证产物签名，不得把 debug 签名当作正式签名。
- iOS 根据目标分发方式配置证书、provisioning 和导出选项；构建成功不等于已经上传或通过审核。
- 将 Android mapping 文件、Dart 混淆符号（如果启用）和 iOS dSYM 等诊断产物按发布版本安全保存；符号文件的产生方式以实际构建配置为准。
- 发布前用发布模式验证首屏、路由、语言/主题、网络配置和平台能力；核对环境、版本、目标渠道、权限声明和签名身份。

### 15.4 Dart 环境与原生 flavor 的关系

首版只有第 5 节的 `APP_ENV` 逻辑环境，不创建 Android flavors 或 iOS schemes，也不提供可并装的环境版本。

如派生项目需要开发/测试/生产版本并行安装，应新增 Android product flavor、对应 iOS scheme 和各自应用标识、名称及服务配置；构建脚本显式把每个 flavor 映射到正确的 `APP_ENV`。例如 `development` 原生 flavor 对应 `APP_ENV=development`；CI 校验映射，不允许生产签名和测试地址意外组合。具体 Gradle、Xcode 配置及 `--flavor` 命令按实施时 Flutter 文档验证，不能认为仅传 `--dart-define` 就完成了原生隔离。

**验收**：Android debug 和 iOS Simulator 构建可在 CI 复现；发布流程可在提供签名后产出正确环境的包；产物版本、标识和签名与记录一致。

## 16. 新项目初始化与扩展

### 16.1 从模板创建项目

以下步骤针对依据本文实现完成并放入版本控制的模板工程；工程位置与标识由实施时确定。本说明不代表工程已经创建或步骤已经验证。

1. 从模板创建独立仓库或复制干净源码，保留模板许可证和来源说明；确认新项目名称、标识及目标平台。
2. 配置项目约定的 Flutter SDK，执行 `flutter doctor`；保留并使用应用工程的 `pubspec.lock`。
3. 修改 `pubspec.yaml` 中的 Dart 包名、描述和版本，并更新对应的 `package:` 导入；检查包名符合 Dart 命名规则。
4. 修改 Android application ID、必要的 namespace/Kotlin 包路径、应用名和图标；修改 iOS Bundle ID、显示名称、图标、Team 和签名配置。检查与构建脚本、深度链接、服务配置相关的引用。
5. 在主题和 ARB 中替换品牌色、应用名称、图标和演示文案；确认字体、图片和第三方资源的授权。
6. 设置开发、测试和生产环境的公开配置；不提交真实凭据。首版保留 Fake 数据源，直到具体服务和协议确定。
7. 运行第 14.2 节基础检查，并在 Android 和 iOS 分别运行；记录已验证的工具链与平台版本。
8. 新建项目自己的 README，写清启动、环境、构建和维护方式；删除不再需要的模板示例。

克隆或复制时是否保留 Git 历史，由项目所有者和许可证要求决定。不要自动删除已有 `.git`、签名材料或用户数据。

### 16.2 模板实例化自动验证

首版不要求编写复杂生成器，但必须提供可重复的实例化脚本或 CI job：从干净模板副本生成临时应用，替换 Dart 包名、Android applicationId/namespace/Kotlin 路径、iOS Bundle Identifier/显示名称，更新 README 和资源；随后按下列分类扫描残留；命中禁止项或精确白名单之外的项即失败。脚本只操作临时副本，禁止依赖人工在开发者工作区执行全局替换。

| 扫描类别 | 判定规则 |
| --- | --- |
| 应用身份与品牌 | 实例化配置显式提供新 Dart 包名、Android 标识/namespace/Kotlin 路径、iOS Bundle ID、名称及品牌文案；源码、原生配置和用户可见资源中的旧值必须清除。 |
| 可执行 API 配置 | 默认保留 Fake 模式、空 base URI；不得写入可访问的示例业务服务地址。API 模式下缺失或占位地址必须校验失败，不允许通过扫描白名单放行。帮助链接与依赖仓库地址不属于业务 API，但需显式配置用途。 |
| 文档、测试及来源说明 | 可保留解释用示例、验证非法配置的测试夹具、许可证及来源标识；在版本控制的扫描配置中逐项记录文件相对路径、允许值/匹配规则及原因，禁止目录级或全域名通配放行。 |
| Fake 演示数据 | 可以保留通用离线数据和相应类型，但用户可见旧品牌仍需替换，不通过删除 Fake 强迫接入后端。 |

扫描范围为实例化副本中受版本控制的文本源码、配置、测试和文档；排除依赖缓存、构建目录及生成文件。使用字面值或按语法解析的匹配，防止含下划线的 Dart 包标识被普通单词边界漏检；原生二进制资源的品牌替换另作资源清单和人工检查。报告列明扫描范围、禁止命中、精确白名单命中及未检查项。CI 必须用旧标识残留、API 占位配置和越界白名单样本证明检查会失败，不能只运行一次“无命中”的正例。

实例化产物须执行 `flutter pub get`、`flutter gen-l10n`、格式检查、静态分析、单测/Widget 测试、Android debug 构建、iOS Simulator 构建。CI 记录模板 commit、SDK/Dart、JDK、Xcode、Android SDK、目标系统版本及结果。此项与模板本身构建分开，防止两类覆盖混淆。

**验收**：从干净检出开始一条命令或一项 CI workflow 可完成实例化和双平台编译；输出报告无未获准的旧身份/品牌残留，且可执行配置不存在示例业务 API 地址；允许的文档/测试例外逐项列出；失败时给出文件、行号及规则。

### 16.3 常见扩展步骤

| 任务 | 推荐步骤 | 完成条件 |
| --- | --- | --- |
| 新增页面 | 在 `features/<feature>/presentation` 建页面和必要状态；在路由表声明路径，加入本地化文案。 | 导航、返回、未知参数和相应 Widget 行为可验证。 |
| 新增状态 | 先判断是否仅为 Widget 局部状态；共享/异步状态再建立 Riverpod Provider，并定义生命周期。 | 明确状态所有者、加载/失败和释放方式。 |
| 新增 API | 配置环境地址；在 API Service 实现协议解析，在 Repository 转换数据和失败；通过 Provider 注入。 | Fake 与错误路径可覆盖；无凭据或敏感数据写入日志。 |
| 新增语言 | 增加 ARB，补齐模板键及元数据，生成本地化代码并更新设置选项与 Locale 匹配策略。 | 新语言、跟随系统、默认回退和缺失翻译检查通过。 |
| 新增平台插件 | 先按第 3.3 节评估；添加适配器与平台声明，核对 Android/iOS 实际行为。 | 不支持、取消、拒绝和失败有处理；工具链与文档已更新。 |
| 新增需要持久化的设置 | 定义稳定的键和值、默认值、读写失败及迁移规则；接入设置仓库和状态。 | 保存失败与重启恢复行为符合约定。 |

首版 README 应链接本文，同时给出无需阅读全文即可运行的最短命令、Fake 数据说明及已知限制。文档路径和示例代码与实际实现发生变化时，随代码一起更新。

## 17. 模板维护与升级

### 17.1 分阶段实施与阶段门

工作按可运行增量实施，每阶段结束前完成验收记录；后续阶段不得把尚未实现的能力标记为模板承诺。

| 阶段 | 范围 | 阶段退出条件 |
| --- | --- | --- |
| A. SDK 与工程骨架 | 查验 Flutter stable / Dart 组合、固定 SDK；生成 Flutter Android/iOS 工程、锁定依赖和基础 CI | 干净检出可获取依赖；Android debug 与 iOS Simulator 首次构建成功；平台最低版本及工具链写入记录 |
| B. 启动与核心 UI | 启动状态机、环境解析、Riverpod 容器、路由、首页/设置、主题与国际化 | 启动失败恢复和系统/手动主题语言行为通过单测与 Widget 测试；离线启动无网络请求 |
| C. 设置存储契约 | 异步偏好、FIFO 写入、失败语义、启动读取和迁移边界 | 第 7.3 节并发矩阵通过；Android/iOS 真机或模拟器重启恢复有记录 |
| D. 网络示例与错误边界 | Dio 客户端、AppException、Fake/API Repository 示范、加载/空/错误/取消 | 默认 Fake 离线运行；注入错误可映射；无自动副作用重试；不访问公网 |
| E. 工程质量与模板化 | 单测/Widget/集成、CI 双平台构建、从模板实例化新应用 | 第 14 章门禁全部通过；独立新项目清除模板标识并通过双平台构建 |
| F. 模板发布说明 | 版本与维护流程、发布/签名说明、可用平台上的 release 模式验证方式 | 发布说明与脚本可审查；发布模式已执行项和待签名验证项分别记录，不要求模板维护者提供真实分发凭据 |

每个阶段交付代码、可重复命令、结果记录和未解决项；不因阶段完成自动推断后续阶段通过。A–F 属于模板首版；派生应用的签名产物、真机发布模式及渠道验证另按第 17.6 节验收，不作为模板无需账号即可运行的前提。

### 17.2 版本与升级节奏

- 模板维护者至少每季度检查 Flutter stable、直接依赖和重要平台工具链变更；安全或关键构建问题按实际影响及时处理。
- 使用 `flutter pub outdated` 了解可升级版本；阅读 Flutter、Dart 和插件的变更记录，先在单独变更中升级并提交 `pubspec.lock`，避免与业务功能混在一起。
- 常规 CI 使用锁文件和固定 SDK，不在每次构建时执行 `pub upgrade`。应用工程提交锁文件的依据见 [Dart 依赖版本管理](https://dart.dev/tools/pub/cmd/pub-upgrade)。
- 优先分组升级：Flutter/Dart 与平台工具链、核心依赖、按需插件。涉及新最低系统版本、行为变更或平台迁移时，在升级说明中写明影响和回退方式。
- 避免长期依赖 `dependency_overrides`；确需临时使用时记录原因、责任人和移除条件，并检查与原生插件的兼容性。

### 17.3 变更与兼容性管理

每次影响公共使用方式的模板更新应记录：变更内容、受影响平台、升级步骤、数据迁移、验证结果和已知限制。模板自身采用清晰的版本号和变更记录；派生项目独立发展，不应假设可以无冲突地直接合并模板所有更新。

团队指定模板维护者，负责通用能力评审、基线升级、验证和版本发布。派生项目在工程说明中记录创建时的模板版本与 commit，并记录后续采用的模板修复及必要偏离。共性修复应回馈模板；模板发布升级说明，由各应用按自身数据、依赖和发布节奏评估并验证后采用。首版以源码模板交付，不要求所有应用在运行时依赖一个共享框架包；只有复用需求得到验证后，才另行评估提取公共包。

如果修改设置键、生成文件位置、目录结构、最低系统版本或初始化 API，应提供迁移说明；有旧安装数据的派生项目需自行选择适用的迁移实现，不能直接复用未经验证的破坏性清理逻辑。

### 17.4 依赖移除与故障回退

定期检查未使用依赖、许可证和维护状态。替换插件时先验证目标平台能力与数据兼容性，保留适配层接口，并通过关键行为测试；移除旧插件后同步删除权限、原生配置和文档。

升级造成故障时，先定位 SDK、锁文件或原生工具链的变化，再回退对应变更并记录；不要仅删除锁文件后随机重新解析依赖。发现需要紧急处理的问题时，由维护者评估受影响版本、发布修复和向派生项目传达迁移步骤。

### 17.5 完成定义

模板首版完成时应同时满足：

1. 第 1.4 节的功能交付标准已实现；默认启动不依赖业务服务。
2. 第 14 节的基础质量门禁通过，平台验证结果及已知限制可追溯。
3. Android 与 iOS 开发构建可复现；发布签名流程有说明，不要求模板携带真实签名。
4. 新项目初始化步骤已由干净检出实际走通，README 和本说明与代码一致。
5. 依赖、平台最低版本、SDK 和许可证已确认；没有真实密钥、账号或私人业务资料进入模板。

本文是开发设计与验收依据；本文未附带模板实现及其验收证据，因此以上完成定义尚未验证。模板交付报告逐项列出检查命令、工具链、设备/系统、结果、证据位置和未覆盖项；文档检查通过不能替代功能、构建或设备验收。

### 17.6 派生应用发布就绪定义

以下仅在派生应用需要正式分发时执行，不与模板首版完成混用：

1. 配置应用自己的标识、公开环境和真实服务协议；按应用用途决定是否继续使用 Fake，不允许误带示例业务服务。
2. 在受控发布环境提供签名材料，生成对应渠道产物，核验环境、版本号、应用标识、签名身份及诊断符号。
3. 使用目标 Android/iOS 真机和 release 模式验证启动、路由、主题/语言、持久化及已启用的平台能力；记录设备和系统版本。
4. 完成渠道要求的权限、资源授权、隐私与服务配置核对，并记录发布和回退步骤。产物已构建不代表已通过渠道审核。

缺少凭据、macOS 或设备时，相关项标记“未执行”并说明限制，不能以模板 CI 的 debug/Simulator 编译成功替代发布就绪证明。
