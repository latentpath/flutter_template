# 维护与升级

复制模板后，当前副本就是独立应用。日常开发和升级都在自己的工程中进行，无需重新生成或复制新工程。

## 采用模板修复（按需）

1. 在自己的 README 或维护记录中保存模板来源地址、版本、commit（如有）或复制日期。准备更新时，先保存当前代码及必要的测试数据。
2. 比较来源模板与当前应用，只选择适用的修复。保留自己的包名、原生标识、品牌、服务、签名和业务代码，避免整目录覆盖。有 Git 时可在独立分支操作。
3. 如果涉及设置键或格式，先设计可重复执行的迁移；成功写入新格式后再考虑删除旧值。验证旧安装数据、失败与重试，不假定代码回退会恢复旧数据。
4. 按 [使用指南的日常检查](USER_GUIDE.md#日常检查与协作) 验证，并在目标设备检查启动、导航和设置恢复。记录实际采用的修改、工具链版本和结果。
5. 出现问题时回退对应补丁、SDK、锁文件或原生配置；涉及持久化迁移时另行评估数据兼容性。

## 升级 Flutter 与依赖

Flutter 版本以 [`.fvmrc`](../.fvmrc) 为准，依赖约束和解析结果分别在 [`pubspec.yaml`](../pubspec.yaml) 与 [`pubspec.lock`](../pubspec.lock)。

```sh
flutter pub outdated
```

先查看需要更新的依赖，再审查兼容性、平台最低版本与插件行为。将 Flutter/Dart、业务依赖和原生工具链分批更新；升级 Flutter 时同步维护 `.fvmrc`，修改依赖时同步维护约束和锁文件。常规运行使用锁文件，不把 `pub upgrade` 作为启动步骤。

每批更新后执行日常检查，并按目标平台验证构建与设备行为。iOS 需在 macOS 上验证；模拟器编译不能代替真机和签名验证。不要通过删除锁文件并随机重新解析来掩盖问题。

## 记录与回退

在自己的维护记录中保存重要更新、兼容性影响、迁移和回退方法；不要求特定文件名或阶段文档。应用版本由 `pubspec.yaml` 管理，准备分发时参照 [发布与签名](RELEASING.md)。
